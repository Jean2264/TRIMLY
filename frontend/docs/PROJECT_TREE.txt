TRIMLY - ÁRBOL DE ARQUITECTURA
================================

Este documento describe la estructura real del repositorio al 19/09/2026.
La aplicación está dividida en un backend Node.js/Express y un frontend React/Vite.
Las carpetas `node_modules` y el contenido interno de `.git` no se documentan porque
son dependencias o metadatos generados, no código fuente del producto.


1. RAÍZ DEL REPOSITORIO
=======================

TRIMLY/
├── .git/                         Control de versiones del proyecto.
├── backend/                      API REST, autenticación y acceso a PostgreSQL.
├── frontend/                     Aplicación web React y documentación funcional.
└── package-lock.json             Lockfile existente en la raíz; conserva dependencias
                                  instaladas a nivel raíz, aunque los scripts de ejecución
                                  están definidos en los package.json de backend y frontend.


2. BACKEND
==========

backend/
├── .env
├── .env.example
├── .gitignore
├── nodemon.json
├── package.json
├── package-lock.json
├── server.js
├── querys/
└── src/

El backend utiliza módulos ES (`type: module`), Express 5, PostgreSQL mediante `pg`,
JWT para sesiones, bcrypt para contraseñas, dotenv para configuración, CORS y Resend
para el envío del correo de activación.

2.1 Archivos de configuración y ejecución
------------------------------------------

backend/.env
  Variables sensibles y específicas del entorno local: conexión a PostgreSQL,
  secreto JWT y configuración del proveedor de correo. No debe versionarse ni
  documentarse con sus valores reales.

backend/.env.example
  Plantilla de las variables que necesita el backend para poder ejecutarse en otro
  entorno sin exponer credenciales.

backend/.gitignore
  Exclusiones del backend para Git, principalmente `.env`, dependencias y archivos
  generados.

backend/nodemon.json
  Configuración de Nodemon para reiniciar el servidor durante el desarrollo cuando
  cambian los archivos del backend.

backend/package.json
  Manifiesto del API. Define el script `dev` (Nodemon sobre `server.js`), habilita
  módulos ES y declara Express, pg, bcrypt, jsonwebtoken, dotenv, cors, crypto,
  resend y Nodemon.

backend/package-lock.json
  Versiones exactas y árbol de dependencias instaladas para reproducir el backend.

backend/server.js
  Punto de entrada del servidor. Importa la aplicación Express y la configuración
  de base de datos, escucha en `0.0.0.0:3000` y deja la aplicación preparada para
  recibir las rutas de health, autenticación, empleados y servicios.

2.2 SQL y base de datos
-----------------------

backend/querys/
  Scripts SQL usados para crear y probar el modelo relacional.

backend/querys/tables.sql
  Script de definición y carga manual de PostgreSQL. Declara las tablas Usuario,
  Rol, Empleado, Servicio, EmpleadoServicio y Cliente; sus claves primarias,
  relaciones, estados, fechas y campos de activación. También contiene alteraciones
  para tokens de activación, código de servicio, datos iniciales de roles y consultas
  de prueba/actualización usadas durante el desarrollo.

backend/src/database/
  Pruebas o utilidades directas relacionadas con la base de datos.

backend/src/database/test.js
  Script de prueba de conexión/operaciones de base de datos. Es una utilidad de
  desarrollo y no forma parte del flujo HTTP principal.

2.3 Núcleo de Express
---------------------

backend/src/app.js
  Construye y exporta la instancia de Express. Habilita CORS y el parser JSON,
  monta `/health`, `/auth`, `/employees` y `/services`, y conserva una respuesta
  simple en `/` para comprobar que el servidor está iniciado.

2.4 Configuración transversal
-----------------------------

backend/src/config/
  Configuración reutilizable por repositorios y servicios.

backend/src/config/db.js
  Carga dotenv, crea el `Pool` de PostgreSQL con DB_HOST, DB_PORT, DB_NAME,
  DB_USER y DB_PASSWORD, comprueba la conexión inicial y exporta el pool para
  ejecutar consultas desde los repositorios.

backend/src/config/jwt.js
  Encapsula la creación de tokens JWT. `generarToken(payload)` firma el payload
  con `JWT_SECRET` y una expiración de una hora.

2.5 Rutas HTTP
--------------

backend/src/routes/
  Define los routers Express. Cada router sólo conecta verbo/URL con un controller;
  la lógica de negocio vive en `services` y el SQL en `repositories`.

backend/src/routes/health.routes.js
  Expone `GET /health/health` y lo conecta con el controller de estado del servidor.

backend/src/routes/auth.routes.js
  Expone `GET /auth/test` para comprobar la ruta, `POST /auth/login` para iniciar
  sesión y `POST /auth/activar-cuenta` para completar la activación de un usuario.

backend/src/routes/employees.routes.js
  Expone el CRUD de empleados bajo `/employees`: `POST /`, `GET /`, `GET /:id`,
  `PUT /:id` y `DELETE /:id` (la baja es lógica mediante estado).

backend/src/routes/service.routes.js
  Expone el CRUD de servicios bajo `/services`: alta, listado paginado/filtrado,
  detalle por id, modificación y baja lógica.

2.6 Controllers
---------------

backend/src/controllers/
  Capa HTTP. Lee params, query y body, llama a un servicio de negocio y traduce el
  resultado a códigos y respuestas JSON.

backend/src/controllers/health.controller.js
  Implementa `health`, que registra la solicitud y devuelve `{ status: "ok" }`.

backend/src/controllers/auth.controller.js
  Implementa `login` y `activarCuenta`. Delega credenciales y activación en
  `usuario.service.js`; en el login genera el JWT y devuelve el usuario con sus
  datos de cliente/empleado y rol.

backend/src/controllers/employees.controller.js
  Implementa alta, listado paginado con búsqueda, consulta individual, actualización
  y baja de empleados. Maneja validaciones/resultados del servicio y errores HTTP.

backend/src/controllers/service.controller.js
  Implementa alta, listado paginado con búsqueda, consulta individual, actualización,
  baja lógica y consulta resumida de servicios para el modal del barbero.

2.7 Services de negocio
-----------------------

backend/src/services/
  Capa de aplicación. Valida datos, coordina repositorios, hashing, tokens y correo,
  sin exponer consultas SQL a los controllers.

backend/src/services/usuario.service.js
  Gestiona login y activación de cuentas. Busca el usuario, valida estado/cuenta,
  compara contraseñas con bcrypt, genera/consume hashes de token con crypto, valida
  expiración y actualiza contraseña/foto al activar.

backend/src/services/employees.service.js
  Valida y crea empleados, genera datos de activación, hashea contraseñas iniciales,
  guarda el empleado mediante el repositorio y envía el correo de activación. También
  encapsula listado paginado, detalle, edición y baja lógica.

backend/src/services/services.service.js
  Valida nombre, costo y duración; coordina alta, listado, detalle, edición y baja
  de servicios. Incluye la consulta resumida/paginada usada por el modal del barbero.

backend/src/services/email.service.js
  Integra el proveedor Resend para enviar al empleado el enlace/token de activación
  de cuenta.

2.8 Repositories
----------------

backend/src/repositories/
  Capa de persistencia. Usa el pool de PostgreSQL y concentra todas las consultas
  SQL del dominio.

backend/src/repositories/usuario.repository.js
  Consulta usuarios para login con joins a Cliente, Empleado y Rol; busca usuarios
  por hash de activación y actualiza la cuenta activada, contraseña, token y foto.

backend/src/repositories/employees.repository.js
  Inserta usuario y empleado dentro de una transacción, lista empleados activos con
  búsqueda/paginación, obtiene uno por id, actualiza sus datos y realiza la baja
  lógica cambiando `estado`.

backend/src/repositories/services.repository.js
  Inserta servicios y genera su código `C###` en una transacción; lista servicios
  activos con búsqueda, orden y paginación; obtiene detalle, actualiza, da de baja
  lógicamente y devuelve una vista reducida para selección del barbero.


3. FRONTEND
==========

frontend/
├── .gitignore

├── package.json
├── package-lock.json
├── README.md
├── vite.config.js

El frontend es una SPA React 19 con Vite, React Router, Bootstrap Icons y Motion.
`main.jsx` monta la aplicación con `BrowserRouter`; `App.jsx` combina el contexto
de autenticación, las rutas públicas, administrativas y del barbero, y el modal global
de autenticación.

4.1 Entrada, API, contexto y hooks
----------------------------------

frontend/src/main.jsx
  Crea la raíz React en `#root`, aplica `StrictMode`, `BrowserRouter`, Bootstrap
  Icons y estilos globales, y renderiza `App`.

frontend/src/App.jsx
  Composición raíz: envuelve todo en `AuthProvider`, monta `PublicRoutes`,
  `AdminRoutes`, `BarberRoutes` y el `AuthModal` global.

frontend/src/api/auth.api.js
  Cliente HTTP mínimo para autenticación. Actualmente exporta `login(email, password)`
  y realiza `POST http://localhost:3000/auth/login` enviando JSON.

frontend/src/context/AuthProvider.jsx
  Contexto de autenticación. Centraliza usuario/token y las acciones/estado que
  consumen formularios y componentes de la aplicación.

frontend/src/hooks/PasswordStrength.jsx
  Hook/componente auxiliar para calcular o representar la fortaleza de una contraseña.

frontend/src/hooks/useImageUpload.js
  Hook para seleccionar/cargar una imagen y administrar su estado o representación
  durante formularios de usuario, empleado o servicio.

5. FLUJO ARQUITECTÓNICO RESUMIDO
================================

1. Vite sirve `frontend/index.html` y `src/main.jsx` monta React.
2. `App.jsx` instala `AuthProvider` y renderiza los tres árboles de rutas.
3. Cada ruta usa un layout y páginas/componentes especializados.
4. Los componentes de autenticación llaman a `src/api/auth.api.js`.
5. El backend arranca en `server.js`, configura Express en `src/app.js` y monta routers.
6. Los controllers traducen HTTP a llamadas de services.
7. Los services validan y coordinan repositorios, bcrypt, JWT y correo.
8. Los repositories consultan PostgreSQL mediante `src/config/db.js`.
9. El esquema y las relaciones principales están descritos en `querys/tables.sql`.

Nota: el inventario refleja los archivos presentes actualmente. Algunas pantallas del
panel y operaciones de reserva todavía funcionan como estructura visual/prototipo y
no necesariamente tienen endpoints backend equivalentes implementados.
